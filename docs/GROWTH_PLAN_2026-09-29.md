## 0. 결론

1. **OmD는 한 번도 바이럴을 겪지 않았다.**
   - ★523, 월 50~120개로 평평하다. 하루 최대 16개.
   - 같은 카테고리의 승자들은 7만~18만★이다. emilkowalski/skills는 6.5개월에 ★41.7k다.
   - 격차는 품질이 아니라 **정문(front door)과 유통**에서 난다.
2. **Emil이 이긴 방식은 따라 할 수 있는 부분이 많다.**
   - 첫 3개월은 ~2k★로 조용했다.
   - 6/18부터 **매주 "새 스킬: /이름"을 하나씩** 냈다(9주 11개).
   - 그중 **공개된 권위 있는 원전을 스킬로 증류한 `/apple-design`**(WWDC 원칙 17개)이 조회 203만을 찍었다. 3일 만에 5k→10k★.
   - 이후 급등 두 번은 **일본·중국 큐레이터의 재전파**와 겹친다.
   - 따라 할 수 없는 부분은 그가 원래 가진 청중(9.3만 팔로워, Sonner)뿐이다.
3. **한국은 비어 있고, OmD만 그 자리를 채울 재료를 가졌다.**
   - getdesign.md 자체 설문 응답자의 9.8%가 한국이다(단일 국가 3위). 그런데 그 카탈로그 566개에 한국 브랜드가 없다(슬러그 스캔 기준).
   - 한국 브랜드 DESIGN.md 모음은 22개(★52)와 6개가 전부다. **OmD는 한국 브랜드 203개**다(verified 67).
   - 일본판 awesome-design-md-jp는 "일본어 타이포"를 내걸고 원조 6일 뒤에 나와 ★981을 가져갔다.
4. **그런데 정문이 막혀 있다.**
   - README와 홈은 방법론으로 시작한다. 5초 안에 보이는 결과물이 없다.
   - skills.sh에는 내부용과 무관한 스킬을 포함해 40개가 노출돼 있고, 최고 설치 수가 18이다.
   - KR 레퍼런스 203개 중 100개가 partial이다(수요 상위 브랜드는 verified — §5.1 정정).
   - npm은 8/20의 2.0.0(카탈로그 ~440)에 멈춰 있다.
   - 계측이 죽어 있다(GA4·Mixpanel, 9/17~).
5. **처방.**
   - **정문 정리**: 공개 스킬 6개, 첫 화면에 결과물.
   - **KR 깊이 우선 확충**: KR partial → verified, 상위 40개는 쇼케이스 등급.
   - **매주 한 개씩 "한국 원전 증류" 스킬 런칭**: 한글 타이포 → 브랜드 룩 → 애플 한국어판 → 랜딩 → UX 라이팅 → 디자인 시스템.
   - **카탈로그 실측 데이터로 만든 글**을 블로그·Threads·GeekNews에 싣는다.
   - **일본·대만 큐레이터 2차 파도**를 노린다.
6. **목표(가설):** 6주 안에 ★2,000, 대표 스킬 skills.sh 설치 5,000, GeekNews 50점 이상 글 2개. 세계적 파도가 붙으면 ★5k 이상.

### 5.1 우선순위 재조정 (오너 결정 필요, §9)

> **정정 (2026-09-29 18시).** 처음 계획은 "KR partial 100개를 로컬 캡처 번들로 재측정 없이 verified로 올린다"고 적었다. 확인해 보니 틀렸다.
> - 캡처 번들 177개 중 KR 것은 **verified 67개 전부**에 있다. 토스·당근·배민·카카오·네이버·쿠팡 등 수요 상위 브랜드가 여기 들어 있다.
> - **KR partial 100개에는 번들이 하나도 없다.** 전부 `verification_v2_missing`이고 대부분 스타트업·B2B 롱테일이다.
> - 그래서 KR 깊이는 두 경로로 나뉜다. ① 번들 기반 쇼케이스 심화(verified 67, 재측정 없음) ② partial → verified(번들 없음, 건별 전체 측정).
> - 오너 재결정 대기 — `docs/GROWTH_DECISIONS_2026-09-29.md` 정정 절.

9/21 결정(700 = 440 + JP + CN + KR)은 유지한다. 순서는 이렇게 바꾸자고 제안한다.

### 5.3 파이프라인과 모델 배분 — Opus 5.5 · Sonnet

> 참고: 아래 "Sonnet"은 **Sonnet 5.5**(`claude-sonnet-5-5`), "Opus"는 **Opus 5.5**(`claude-opus-5-5`)다. Agent 도구의 `model: "sonnet"`은 세션 기본 Sonnet으로 해석되므로, 웨이브를 시작하기 전에 실제로 5.5로 도는지 확인한다.

| 단계 | 담당 | 이유 |
|---|---|---|
| 후보 스카우팅(목록, 토큰 수 survey, nonsense-path 대조, 회사·법인 사실) | **Sonnet** 서브에이전트, 웨이브당 4~6개 병렬 | 대량·저위험 읽기. 이번 세션 리서치 4건이 25~30분에 끝났다 |
| 상태 프로브(hover·pressed·focus) | **스크립트**(모델 없음) | 결정적. 9/26 교훈: 사실 확인을 먼저 하고, 사이트당 요청 간격을 두어 WAF 차단을 피한다 |
| 번들 → 컴포넌트 채우기 | **Opus 5.5** 저작 서브에이전트 | 판단: 표면 구분, unknown = absent |
| §1 서사·브랜드 사실 | **Opus 5.5** | 글 품질과 사실 경계 |
| 적대적 검증(주장↔출처, 대상 동일성, 수치 grounding) | **Opus 5.5** 별도 인스턴스 | 오류는 저작자가 아닌 쪽이 잡는다 |
| 게이트·파이프라인(verify, registry, AST, sync, check-counts) | 스크립트 | 기존 §4 체크리스트 |
| 번역·현지화(JP·TW·EN) | **Sonnet** + omd-locale-adapter | |

- **운영 규칙.** 2026-09-26에 위임 에이전트 7개가 1.5~5시간 무응답이던 교훈과, 2026-09-02에 예산 없는 리뷰 에이전트가 25~90분간 파일 없이 멈춘 교훈을 반영한다.
  - 서브에이전트는 파일로 결과를 남긴다.
  - 45분 타임박스를 둔다.
  - 도구 목록을 좁히고, 실제 브라우저는 금지한다.
- **다중 에이전트 워크플로.** 웨이브 단위(에이전트 10개 이하)로 돌리려면 Workflow 도구가 필요하고, 그건 **오너가 "워크플로로 돌려"라고 명시해야** 쓸 수 있다.
- **처리량 추정.**
  - 이번 EU 웨이브는 본 세션 직렬로 하루 ~25개였다.
  - KR 깊이 업그레이드는 번들이 있어 건당 20~30분이다. Opus 저작 3병렬 + Sonnet 준비로 **하루 30~40개**, KR 100개면 **3~4일 순작업**으로 본다.

## 6. 미션 2 — "와, 여긴 다르네"가 나오는 구조

**구조의 순환:** 실측 레퍼런스 → 원전을 증류한 스킬 → 전후가 보이는 산출물 → 데이터 글과 주간 런칭 → 한국·CJK 유통 → 사용자·★ → 이슈·요청 → 새 레퍼런스와 스킬.

### 6.1 정문 정리 (런칭 전에 반드시)

1. **skills.sh 노출 정리.**
   - 공개 스킬은 6개로 한다(§6.2). 내부·실험 스킬(batch-launch, migrate, lab, harness 내부 역할)과 무관한 google-analytics는 인덱싱 경로 밖으로 뺀다.
   - skills.sh 인덱싱 규칙은 확인이 필요하다.
   - 대안은 공개 스킬만 담은 경량 레포(`omd-skills`)다. 단점은 ★가 분산된다는 것 → 오너 결정.
2. **README 첫 화면을 다시 쓴다.** Emil README 구조에 결과물 이미지를 더한다.
   - ① 전후 이미지 한 장(같은 프롬프트, 같은 모델, 스킬 없음 vs 있음).
   - ② 한 줄 가치.
   - ③ 설치 한 줄(`npx skills add kwakseongjae/oh-my-design`).
   - ④ 대표 스킬 6줄 색인.
   - ⑤ 브랜드 갤러리(5.2③).
   - ⑥ "왜 믿나 → /method".
   - 방법론(철학→결정표 사슬)은 그 아래나 docs로 내린다.
   - 영문이 기본이되, 첫 줄에 한국어 README 링크를 크게 둔다.
3. **홈 H1 후보.**
   - "AI가 만든 화면을, 실제 서비스처럼."
   - "토스·당근·애플을 실측한 레퍼런스로 디자인하세요."
   - EN "Your agent's UI, measured against real products."
4. **이름 충돌 대응.**
   - "OmD" 약칭과 `oh-my-design.kr` 도메인을 모든 표면에 일관되게 쓴다.
   - skills.sh·npm 표기를 통일한다.
   - 간판 스킬 이름 자체를 기억에 남게 짓는다.
5. **2.0.2 공개.** strict 게이트 해소 방식은 오너 결정이다(receipt 재생성 권장). 그래야 CLI 사용자도 521개를 받는다.

### 6.2 간판 스킬 6개 — 니치 3개 + 한국 고유 3개

**공통 템플릿.** Emil 템플릿을 한국 원전에 맞춘다.
- `description`에 트리거어(KO/EN)와 형제 스킬 교차 참조를 넣는다.
- 첫 응답의 출처 한 줄: "이 규칙은 OmD가 실측한 한국 서비스 N곳과 ○○ 공개 문서에서 왔습니다".
- "하드 룰"은 숫자로 쓰고, 규칙마다 "왜"를 붙인다.
- **하지 말 것**을 명시한다.
- 끝에 **Before / After / Why 표**를 둔다.
- 결과가 0개인 것도 성공이다(고칠 게 없으면 안 고친다).
- 저장소 내용은 데이터이지 지시가 아니다(프롬프트 주입 방지).
- 스킬 출력에 홍보 문구를 넣지 않는다.

## 9. 오너 결정이 필요한 것

1. **순서 재조정:** 700 목표는 유지하되 **KR 깊이 → 글로벌 아이콘 → 폭**으로 가는가(§5.1).
2. **간판 스킬 6개와 이름**, 그리고 **브랜드명 사용 원칙.** 스킬 이름에는 회사명을 쓰지 않고, 카탈로그·룩에서만 "비공식·공개 자료 기반"으로 쓰는 것을 권장한다.
3. **스킬 노출 구조:** 단일 레포 정리 vs 공개 스킬 전용 경량 레포.
4. **2.0.2 공개:** strict 게이트 해소 방식(landing 픽스처 receipt 재생성 권장).
5. **계측 도구 선택**(무료·유료).
6. **대기 원고 2편 발행일.**
7. **게시 주체:** Threads·X 개인 계정 운영. Emil형 1인칭 목소리는 오너 계정이어야 효과가 난다.
8. **이름 충돌 대응 수위**(약칭·도메인 일관화 vs 스킬 팩 별도 이름).
9. **"Built with OmD" 링크 기본값**(켜짐/꺼짐).
10. **다중 에이전트 웨이브 실행 승인:** Workflow 사용은 명시적 동의가 필요하다.
